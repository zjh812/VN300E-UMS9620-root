## 0. 结论速览

官方脚本的 3 个 mismatch **不是**「这版 U-Boot 没有等价路径」，而是**同一份 Unisoc u-boot15 代码被换了个链接基址/编译单元排布**。按函数边界 + 字符串字面量 XREF + 跳表 + AArch64 反汇编重新推导后，官方 4 个 patch 点在你这版固件里**全部存在语义等价物**：

| 官方 code offset | 本机 code offset | 文件 offset | 匹配强度 |
|---|---|---|---|
| `0x604c0` (get_lock_status 强制 UNLOCK) | **`0x62830`** | `0x62A30` | 掩码级匹配（同 opcode + 同 Rt，仅 imm19 漂移） |
| `0x0afe8` (去掉 UNLOCK 警告分支) | **`0xB504`** | `0xB704` | **原始 32 位指令完全相同** `0x54000180` |
| `0x0b2a4` (SKIP_VERIFY UART 调用) | **`0xB7B8`** | `0xB9B8` | 函数内相对偏移完全相同（`+0x6C`） |
| `0x0b2ac` (SKIP_VERIFY 屏幕调用) | **`0xB7C0`** | `0xB9C0` | 函数内相对偏移完全相同（`+0x74`） |

**最强的等价性证据**（不只是"找到一条类似指令"）：

| 参考 build | 本机 build | 函数内相对偏移 |
|---|---|---|
| `0xafc4` 函数入口 → `0xafe8` patch | `0xb4e0` 函数入口 → `0xb504` patch | 两边都是 **`+0x24`** ✅ |
| `0xb238` 函数入口 → `0xb2a4` patch | `0xb74c` 函数入口 → `0xb7b8` patch | 两边都是 **`+0x6C`** ✅ |
| `0xb238` 函数入口 → `0xb2ac` patch | `0xb74c` 函数入口 → `0xb7c0` patch | 两边都是 **`+0x74`** ✅ |

即：函数内部结构是**逐字节同构**的，只有函数的链接基址平移了。这是比"opcode 类型相同"强得多的证据。

## A. 镜像结构

### A.1 文件与哈希

| 项 | 值 |
|---|---|
| 文件大小 | `3145728` = `0x300000` 字节（与 `uboot_b` 分区大小一致） |
| SHA256 | `5935075bed5b12d35b961d0e39a4e95154b8cfb94ac177f96919700a24b8e321` ✅ |
| 尾部填充 | `0x171AE4 .. 0x300000`，共 **1631516 字节全 0**（纯 padding，无数据） |

### A.2 DHTB header（file `0x000000 .. 0x000200`，0x200 字节）

| 偏移 | 字段 | 值 |
|---|---|---|
| `0x00` | magic | `"DHTB"` |
| `0x04` | version | `0x1` |
| `0x08` | data_hash (32B) | `2aa169640d5c8247210c0d39568046bd8223a8e42f0a38487e117b733c914fe7` |
| `0x28` | marker1 | `0xcccccccc` |
| `0x2c` | marker2 | `0xaaaaaaaa` |
| `0x30` | data_size (u64) | **`0x171630`**（1513008 字节） |
| `0x38` / `0x40` | 0 | `0` |
| `0x48` | u64 | `0x0017163000000000`（低 32 位 = data_size 的镜像副本） |
| `0x50` | u64 | `0x0000000000171cc8` |
| `0x58` / `0x60` | 0 | `0` |

**完整性校验**：`SHA256(file[0x200 : 0x200+0x171630]) == DHTB.data_hash` → **✅ OK**

> 也就是说：**这版 DHTB 的 hash 就是 payload 的连续 SHA256**。这与官方文档中"T820 上 DHTB hash 不等于 SHA256(payload)"的描述不同——说明你这版镜像的 DHTB 签名策略与 Anbernic T820 那台不完全一样（这点值得后续单独验证，见 D 节）。

### A.3 SIMGHDR footer

`"SIMGHDR\0"` 在 payload 内只出现 **1 次**，位于 file `0x171830`（= `0x200 + data_size`，紧贴 payload 尾部，无 gap）。

| 偏移（相对 SIMGHDR） | 字段 | 值 |
|---|---|---|
| `+0x00` | magic | `SIMGHDR\0` |
| `+0x10` | data_size | `0x171630` |
| `+0x18` | header_size | `0x200` |
| `+0x20` | sig_struct_size | `0x458` |
| `+0x28` | total_offset | `0x171890` |
| `+0x60` | flags | `0100000000100000` |
| `+0x68` | RSA exponent | `65537` (`0x10001`) |
| `+0x6C` | RSA modulus | `a1122eb2580834e4e6d26fb8943899f6…` |
| `+0x16C` | data_hash_copy | `d311873c88107d9f9eac000b6a895c14d8e4e263b0e85d82e5779e9dc30e705e` |
| `+0x18C` | second_hash | `641234ffff9ed0b16f83926d6c04ba0e443b33a6d25d5bdab43c49f52d387d3c` |
| `+0x1B4` | signature (256B) | `dade0782b8a28fa69b9af1990367b717…`，**非全 0 → 镜像已正式签名** |
| `+0x2B4` | SIMGHDR 结束 | file `0x171AE4` |

注意：`SIMGHDR.data_hash_copy` **≠** `DHTB.data_hash`。两者覆盖范围不同（DHTB 只覆盖 payload；SIMGHDR 的 hash 覆盖范围更大），因此不能把两个 hash 混为一谈。

### A.4 地址空间划分（本报告全篇统一用这套记法）

| 概念 | 定义 | 范围 |
|---|---|---|
| **字符串文件 offset** | 直接文件字节位置 | `0x000000 .. 0x300000` |
| **U-Boot payload 文件 offset** | payload 在文件中的位置 | `0x000200 .. 0x171830` |
| **code offset（代码偏移）** | `code_off = file_off - 0x200` | `0x000000 .. 0x171630` |
| **DHTB header offset** | `0x000000 .. 0x000200` | header |
| **SIMGHDR header offset** | `0x171830 .. 0x171AE4` | footer |
| **runtime VA** | 本报告**不推导**（需要 magic64 打包参数，超出"只读逆向"范围） | — |

> ⚠️ 你给的那批字符串偏移（`0xD4BC8` / `0xD23D8` …）是**文件 offset**；本报告的字符串偏移是 **code offset**，两者相差 `0x200`。例如 `VerifiedBoot-UNLOCK`：文件 `0xD4BC8` = code `0xD49C8`。
>
> **绝对不要把字符串的 code offset 当成代码地址。** 本报告里所有"代码位置"都经过反汇编验证，标注为函数入口或指令偏移。

### B.1 逐点证据

#### ① code `0x62830` — `get_lock_status()` 内的 LOCK/UNLOCK 判定

函数入口 `0x627A4`（`stp x29, x30, [sp, #-0x30]!`），由字符串 `get_lock_status` @`0xD21D8` 的 XREF 落在 `0x62878` 确认。

```
0x627A4  stp  x29, x30, [sp, #-0x30]!
0x627A8  mov  x0, #0x1dc              ; malloc(476) —— 与参考 "malloc(476)" 一致
0x627BC  str  wzr, [x20, #0x8c8]      ; g_DeviceStatus = 0
0x627C0  bl   #0x303E4                ; malloc
0x627D4  bl   #0x33DF4                ; memset(buf, 0, 476)
0x627E0  bl   #0x622A0                ; read_lock_flag(buf, 1) -> w0
0x627E4  cbz  w0, #0x62808            ; 读成功 -> 走 flag 比对路径
0x62808  ...                          ; 扫描 buf，全 0 则告警
0x6282C  bl   #0xB5A8                 ; sprd_sec_verify_lockstatus(buf, 0x40)
0x62830  cbnz w0, #0x62884            ; ★ 非 0 => LOCK（跳去打印 "%s lock status is locked."）
0x62834  mov  w0, #1
0x62838  mov  w21, w0
0x6283C  str  w0, [x20, #0x8c8]       ; g_DeviceStatus = 1  => UNLOCK
0x62840  b    #0x627EC                ; free + return 1
```

* **原指令**：`0x350002A0` = `cbnz w0, #0x62884`
* **目标**：`0xD503201F` (nop) → 永远 fall-through → `g_DeviceStatus = 1`、返回 `1`
* **与官方 `0x604c0` 的语义等价性**：官方文档描述为 `malloc(476) → common_raw_read(productinfo,476,0x2000,buf) → sprd_sec_verify_lockstatus(buf,0x40) → cbnz w0, LOCK @0x604c0 → 写 1/0 到 g_DeviceStatus`。本机 `0x627A4` 的**结构逐条对应**：`malloc(0x1dc=476)` ✅、读锁标志（本机为 `read_lock_flag()` @`0x622A0`，对应官方的 `common_raw_read`）✅、`verify(...,0x40)` ✅、`cbnz w0, LOCK` ✅、fall-through 写 `1` ✅。
* 差异仅在于本机在 `verify` 前多了一段「扫描 buf 是否全 0」的循环（`0x62808–0x62820`），这解释了为什么函数内偏移是 `+0x8C` 而参考是 `+0x50`。
* 掩码验证：`0x350002A0 & 0xFF00001F = 0x35000000`；`0x35000160 & 0xFF00001F = 0x35000000` → 与官方工具的掩码约定一致。

#### ② code `0xB504` — 启动期锁警告函数的 UNLOCK 分支

函数入口 `0xB4E0`（`stp x29, x30, [sp, #-0x20]!`），由 `bl 0xB4E0` @`0x1F640`（启动校验主流程）确认被调用。

```
0xB4E0  stp  x29, x30, [sp, #-0x20]!
0xB4EC  bl   #0x627A4                ; ★ 调 get_lock_status()
0xB4F0  adrp x0, #0x17b000
0xB4F4  add  x0, x0, #0x200
0xB4F8  ldr  w0, [x0, #0x6c8]        ; w0 = g_DeviceStatus
0xB4FC  cbz  w0, #0xB518             ; 0 => LOCK 分支
0xB500  cmp  w0, #1
0xB504  b.eq #0xB534                 ; ★ 1 => UNLOCK 分支（本 patch 点）
0xB508  mov  w0, #0                   ; fall-through：静默返回 0
0xB50C  ldr  x19, [sp, #0x10]
0xB510  ldp  x29, x30, [sp], #0x20
0xB514  ret
0xB518  ... adrp/add -> 0xBAAA0 "INFO: LOCK FLAG IS : LOCK!!!\n" ; bl 0x32E44 (UART)
0xB534  adrp x19, #0xba000
0xB538  add  x0, x19, #0xac0         ; 0xBAAC0 "INFO: LOCK FLAG IS : UNLOCK!!!\n"
0xB53C  bl   #0x32E44                ; UART 打印
0xB540  adrp x2, #0x198000 ; add x2, x2, #0xb8
0xB548  ldr  w1, [x2] ; cbz w1, #0xB548   ; 自旋等 [0x1980b8] != 0（等显示就绪）
0xB550  add  x0, x19, #0xac0
0xB554  bl   #0x87AB4                ; 屏幕打印
0xB558  mov  w0, #0 ; ... ret
```

* **原指令**：`0x54000180` = `b.eq #0xB534`
* **目标**：`0xD503201F` (nop) → `g_DeviceStatus==1` 时不再跳进 UNLOCK 警告分支，直接 `mov w0,#0; ret`（干净返回，无副作用）
* **与官方 `0x0afe8` 的语义等价性**：
  * 官方 `0xafe8` 的 stock word 是 `0x54000180` —— 本机 `0xB504` **逐位相同**。
  * 官方文档：`0xafc4` 函数「调 get_lock_status → 读 g_DeviceStatus → 分支 LOCK(0xaffc) / UNLOCK-warning(0xb018)」；本机 `0xB4E0` 完全同构。
  * 官方 `0xafc4→0xafe8` 相对偏移 `+0x24`；本机 `0xB4E0→0xB504` 相对偏移 `+0x24` —— **完全相同**。
  * 官方文档还提到 `b.eq` 之后 LOCK 分支在 `0xaffc`；本机 LOCK 分支在 `0xB518`，同样是 `cbz` 直接跳过去。

#### ③ / ④ code `0xB7B8` / `0xB7C0` — SKIP_VERIFY 状态打印函数的跳表 unlock 分支

函数入口 `0xB74C`，由 `bl 0xB74C` @`0x1F664`（启动校验主流程）确认被调用。

```
0xB74C  stp  x29, x30, [sp, #-0x20]!
0xB750  adrp x1, #0x198000 ; add x1, x1, #0xb8
0xB760  ldr  w0, [x1] ; cbz w0, #0xB760   ; 自旋等初始化完成
0xB768  adrp x0, #0x2ca000
0xB76C  ldr  w0, [x0, #0xda0]             ; w0 = 校验结果状态 [0x2CADA0]
0xB770  cmp  w0, #3
0xB774  b.ls #0xB794                      ; <=3 走跳表
0xB778  ... 0xBAD50 "WARNNING: VERIFY RESULT UNKNOWN!!!\n" ; bl 0x32E44
0xB794  adrp x1, #0xb7000
0xB798  add  x1, x1, #0x478               ; 跳表基址 0xB7478
0xB79C  ldrb w2, [x1, w0, uxtw]
0xB7A0  adr  x3, #0xB7AC
0xB7A4  add  x2, x3, w2, sxtb #2
0xB7A8  br   x2                           ; ★ 跳表分发
0xB7AC  adrp x19, #0xba000
0xB7B0  add  x19, x19, #0xd18             ; 0xBAD18 "WARNNING: LOCK FLAG IS : UNLOCK, SKIP VERIFY!!!"
0xB7B4  mov  x0, x19
0xB7B8  bl   #0x32E44                     ; ★ PATCH ③ UART 打印
0xB7BC  mov  x0, x19
0xB7C0  bl   #0x87AB4                     ; ★ PATCH ④ 屏幕打印
0xB7C4  mov  w0, #0 ; ldr x19 ; ldp ; ret
```

跳表 `0xB7478` 实测字节 `16 0A 00 1D`，`target = 0xB7AC + byte*4`：

| 状态 [0x2CADA0] | 跳表字节 | 目标 | 打印内容 |
|---|---|---|---|
| 0 | `0x16` (22) | `0xB804` | `c calcout 0x%x, org 0x%x` |
| 1 | `0x0A` (10) | `0xB7D4` | `WARNNING: your device has loaded a different operating system.` + `USER KEY VERIFY SUCCESS!!!` + **10 秒电源键倒计时** `bl 0xB33C`(w0=0x64) |
| **2** | **`0x00`** | **`0xB7AC`** | **`WARNNING: LOCK FLAG IS : UNLOCK, SKIP VERIFY!!!`（UART + 屏幕）← ③④ 所在分支** |
| 3 | `0x1D` (29) | `0xB820` | `WARNNING: NO VALID OS FOUND!!!` + 30 秒倒计时 `bl 0xB33C`(w0=0x12C) |

**状态 2 从哪来**：函数 `0x61098` 读 `g_DeviceStatus`：
```
0x610A4  ldr  w3, [x3, #0x8c8]      ; g_DeviceStatus
0x610B0  b.eq #0x610EC              ; ==1 → str 2 到 [0x2CADA0]
0x610EC  str  w1, [x0, #0xda0]      ; [0x2CADA0] = 2
```
即 **`g_DeviceStatus==1` ⇒ 状态 2 ⇒ 跳表落到 `0xB7AC` ⇒ 打印 SKIP_VERIFY 那行**。这与官方文档「`SKIP VERIFY` 行来自一个独立的状态打印函数，通过跳表 `br x2` 分发，unlock case 加载字符串并打印两次（UART + 屏幕）」**结构完全一致**。

* 官方 `0xb238→0xb2a4` = `+0x6C`；本机 `0xB74C→0xB7B8` = `+0x6C` ✅
* 官方 `0xb238→0xb2ac` = `+0x74`；本机 `0xB74C→0xB7C0` = `+0x74` ✅

## D. patch 安全性评估

### D.1 确定匹配（可直接采信）

| 点 | 强度 | 依据 |
|---|---|---|
| **② `0xB504`** | ★★★★★ | 原指令与官方 `0x0afe8` **逐位相同**（`0x54000180`）；函数内相对偏移 `+0x24` 与官方**完全一致**；函数结构（调 get_lock_status → 读 g_DeviceStatus → cbz LOCK / cmp#1+b.eq UNLOCK）逐条对应 |
| **③ `0xB7B8`** | ★★★★★ | 函数内相对偏移 `+0x6C` 与官方**完全一致**；跳表 `br x2` + unlock 分支加载 `WARNNING: LOCK FLAG IS : UNLOCK, SKIP VERIFY!!!` 后连打两次（UART+屏幕）——与官方描述逐条对应 |
| **④ `0xB7C0`** | ★★★★★ | 同 ③，相对偏移 `+0x74` 与官方**完全一致** |
| **① `0x62830`** | ★★★★☆ | 掩码级匹配（`0xFF00001F` 下与官方 stock 一致）；函数结构 `malloc(476) → read → verify(...,0x40) → cbnz w0, LOCK → 写 1/0` 逐条对应。**唯一差异**是本机在 verify 前多一段「buf 全 0 扫描」循环，导致函数内偏移为 `+0x8C` 而官方为 `+0x50` |

### D.2 只是候选 / 需人工确认

* **① 的偏移差异**：官方 `0x604c0` 与「verify 调用」的相对位置是 `+0x50`，本机 `0x62830` 是 `+0x8C`。这是本机多出的 `0x62808–0x62820` 全 0 扫描循环造成的。**建议人工确认点**：`0x62830` 之前确实只有这一个 `cbnz w0`（本报告已扫描确认），且 `0x62884` 确实是 LOCK 告警块（打印 `%s lock status is locked.` @`0xD4A50`）。
* **runtime VA / load base**：官方文档称 T820 load base = `0xb5000000`、`mImgAddr` 为占位符 `0xaaaaaaaacccccccc`。**本次只读分析没有重新推导本机的 load base 与 runtime VA**。如果你后续要用 magic64 方式打包，这一步必须单独验证（方法：BSS/SP 字面量 + PAC XML image base），**不要直接套用 `0xb5000000`**。
* **DHTB hash 语义**：官方文档明确说"T820 上 DHTB hash 不是 `SHA256(payload)`"，但**你这版镜像实测就是 `SHA256(payload)` 且校验通过**（A.2）。这说明两台的签名/校验策略不同。这意味着：
  * 直接改 payload + 重算 DHTB hash **有可能**通过校验（但也可能被 SIMGHDR 的 RSA 证书链二次拦截——SIMGHDR 的 RSA 签名确实非 0）。
  * **本报告不做任何结论**，因为"是否可通过"属于可写/可刷阶段，超出本次只读范围。**这一条是本次分析中最需要你亲自确认的风险点。**

### D.3 是否存在不同于参考 T820 build 的额外锁定检查

**存在，且比参考 build 多。** 本机 `g_DeviceStatus` 共有 **14 处**访问点，其中至少 6 处在参考文档里没提到：

```

0x00B4F8  fn 0x00B4E0   ldr w0, [x0, #0x6c8]     ← 启动期锁警告（②）
```

**关键推论（安全性上非常重要）**：
> 因为这 14 处**全部读同一个 `g_DeviceStatus`**，所以 **patch ①（`0x62830`）是"总开关"**——一旦 `get_lock_status()` 恒定返回 `1`，那么：
> * `read_is_device_unlocked()` 自动返回 `*out_is_unlocked = 1` → AVB 侧不再视设备为 locked；
> * `androidboot.flash.locked` 自动变成 `=0`；
> * `0x612C8` 的逐分区 skip-verify 路径自动被激活（`cmp #1` 成立）；
> * `0xB74C` 的跳表状态自动变成 2。
>
> 反过来说，**只打 ① 不打 ②③④** 的结果是：设备在语义上已解锁，但屏幕上仍会打印 UNLOCK 警告和 SKIP VERIFY 警告。②③④ 是"纯观感"补丁。

### D.4 关于「10 秒超时」——本机与参考 build 的**实质差异**（请重点看）

官方文档说 `0x0afe8: b.eq → nop` 会「去掉 INFO_UNLOCK 行 **+ 10 秒超时**」，因为官方 build 的 UNLOCK 分支里在 `0xb040` 有 `bl 0xae68`（倒计时）。

**你这版固件不是这样。** 本机 `0xB4E0` 的 UNLOCK 分支（`0xB534–0xB564`）只有：
1. `0xB53C bl 0x32E44` — UART 打印 `INFO: LOCK FLAG IS : UNLOCK!!!`
2. `0xB548–0xB54C` — 自旋等待 `[0x1980B8] != 0`（等显示就绪，**不是**超时）
3. `0xB554 bl 0x87AB4` — 屏幕打印
4. `0xB558` 返回

**没有电源键倒计时。** 电源键倒计时函数是 **`0xB33C`**（`w0` = 循环次数；每轮 `bl 0x1FFC8` 一次忙等，`0x1FFC8` 是 ARM generic timer 忙等原语：设 `cntp_tval_el0 = 0x6590` 后轮询 `cntpct_el0`）：

| 调用点 | `w0` | 时长 | 所属路径 |
|---|---|---|---|
| `0xB4DC` (`b`) | `0x64`=100 | 约 10 s | fn `0xB4A0` — **死代码（无调用者）** |
| `0xB6EC` | `0x12C`=300 | 约 30 s | fn `0xB680` — 设备损坏告警（`0x1F668` 调用） |
| `0xB7F0` | `0x64`=100 | 约 10 s | fn `0xB74C` **跳表状态 1**（"loaded a different OS"） |
| `0xB83C` | `0x12C`=300 | 约 30 s | fn `0xB74C` **跳表状态 3**（"NO VALID OS FOUND"） |

**结论**：
* 本机 **unlock 路径上不存在电源键超时**，所以 **② 只需承担"去掉警告文字"，不需要额外再 NOP 任何倒计时**。
* 因此你的固件在解锁路径上**本来就比官方 T820 那台少一个 10 秒等待**。这是结构差异，不是漏掉了 patch 点。
* 反过来说：**如果你的目标是"解锁后完全静默且立刻启动"，②③④ 一起打就够了，不存在"还漏了一个超时调用"的情况。**
* 若你希望连状态 1/3 的 10 s / 30 s 也一并去掉，那需要额外 NOP `0xB7F0` / `0xB83C`（`bl #0xB33C`）——**但这会改变"设备被篡改"时的用户可见行为，属于语义扩展，本报告不建议默认采用。**
