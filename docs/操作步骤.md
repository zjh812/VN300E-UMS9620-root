## ⚠️ 动手前必须知道的 3 件事

### 1. 你的设备**已经解锁了**

证据（都是你自己留下的文件）：

| 文件 | 内容 |
|---|---|
| `backup\T9100_back\miscdata.bin` 的 `0x2000` 处 | **全 0** ← 备份时 = LOCKED |
| `unlock_ums9620\dramtype2\m.bin`（解锁脚本读回） | `f4c2f1bf…4c33` + `d78e5fb6aec6af2189fe9d14cbdf3f27` ×2 ← **非全 0，且末 32 字节是两段相同 hash** |
| `miscdata_orig_2000.bin`（你保存的原始值） | 全 0 |

按官方判据「64 字节全 0 = 仍锁定；非 0 + 16 字节 hash + 16 字节 hash = 已解锁」→
**当前状态 = 已解锁 ✅**

**所以不要再跑 `unlock_autopatch_9620.bat` 了。**

### 2. ❌ 不要刷 `uboot_b_patched_skipverify.bin`

那个文件（今天 20:48 生成，3145728 字节）是**直接字节改写**，不是 magic64。实测：

| 检查 | 结果 |
|---|---|
| 改动位置 | file `0x0651FC` / `0x065240`（code `0x64FFC` / `0x65040`，secure-vboot-verify 区的分支强制） |
| 改动字节数 | 6 |
| DHTB `data_hash` | `2aa16964…4fe7`（**未更新**） |
| `SHA256(该文件 payload)` | `878e0f55…92c8` |
| **hash 匹配** | ❌ **False** |
| SIMGHDR RSA 签名 | 覆盖 payload → **已失效** |

这正是官方文档警告的情形：*"on a fused T820 the SPL RSA-verifies uboot, so a modified + rehashed uboot is rejected"*。
**它极可能被 SPL 拒绝（不启动）。** 而且它和 magic64 是两条完全不同的路子。

### 3. ✅ 用 magic64 镜像（payload 逐字节不变 → hash 与签名都还有效）

## 操作流程

### 第 0 步 — 只读：先确认当前 `uboot_b` 里到底是什么

这一步**只读不写**，先摸清现状。设备**完全关机** → 按住 **音量-** 不松手，插入 USB。

```bat
cd /d C:\Users\admin\Desktop\B\T9100\unlock_ums9620\dramtype2
spd_dump --wait 300 exec_addr 0x65012f48 fdl fdl1-dl.bin 0x65000800 fdl fdl2-dl.bin 0xb4fffe00 exec r uboot_b reset
```

读回来会生成 `uboot_b.bin`，核对：

```bat
certutil -hashfile uboot_b.bin SHA256
```

| 结果 | 含义 |
|---|---|
| `5935075bed5b12d35b961d0e39a4e95154b8cfb94ac177f96919700a24b8e321` | ✅ 活动槽是原厂 uboot，可以继续 |
| 其他值 | ⚠️ 停下来告诉我这个 hash |

> **顺便解答一个隐患**：解锁脚本里用的是 `w uboot`（不是 `w uboot_b`）。
> GPT 里只有 `uboot_a`（第 7 项）和 `uboot_b`（第 8 项），**没有裸 `uboot`**。
> 所以 `w uboot uboot_bak.bin` 很可能写到了 **slot A**，而你在用的 slot B 没被动过。
> 第 0 步就是来确认这件事的。
>
> **后面所有写操作都用明确的 `uboot_b`，不要用 `uboot`。**

### 第 1 步 — 刷「机制探针」镜像（零功能影响）

把探针镜像拷进工具目录：

```bat
copy "C:\Users\admin\WorkBuddy AI\2026-10-01-19-11-32\T9100_uboot_b_probe_unlockmsg_magic64.img" .\probe.img
certutil -hashfile probe.img SHA256
```

应得：`d531588b02a0bff4aef863e75c02bb805022c2419408d1404ec0425c2ef5b5c8`

再进 BROM，刷入：

```bat
spd_dump --wait 300 exec_addr 0x65012f48 fdl fdl1-dl.bin 0x65000800 fdl fdl2-dl.bin 0xb4fffe00 exec w uboot_b probe.img reset
```

**这个镜像只改了一件事**：把 code `0xB53C`（UNLOCK 分支里 `INFO: LOCK FLAG IS : UNLOCK!!!`
的 UART 打印 `bl`）改成 `nop`。**不动锁状态、不动校验、不动任何其它东西。**

> 为什么用这个点：你的设备**已解锁**，每次启动都会走 UNLOCK 分支打印这一行
> → 必然可观测；而且它只是一行日志 → 功能零影响。

**读结果**（UART，921600n8，你之前用 COM3）：

| 现象 | 含义 | 下一步 |
|---|---|---|
| `INFO: LOCK FLAG IS : UNLOCK!!!` **消失** | ✅ magic64 执行了 | 进第 2 步 |
| 输出与原来**完全一致** | ⚠️ magic64 没执行（入口点假设不成立） | **停**，设备无损，把日志发我 |
| 设备卡住 | ❌ 最坏情况 | 回滚（见文末） |

### 第 2 步 — 探针生效后，刷完整镜像

```bat
copy "C:\Users\admin\WorkBuddy AI\2026-10-01-19-11-32\T9100_uboot_b_unlock_magic64.img" .\full.img
certutil -hashfile full.img SHA256
```

应得：`dfe33c1501ee2988d46ccf9531712845dbd2779b4e427d95cbd0f0d988b7f39e`

```bat
spd_dump --wait 300 exec_addr 0x65012f48 fdl fdl1-dl.bin 0x65000800 fdl fdl2-dl.bin 0xb4fffe00 exec w uboot_b full.img reset
```

### 第 3 步 — 验证

UART 侧应看到这三行全部消失：
- `INFO: LOCK FLAG IS : UNLOCK!!!`
- `WARNNING: LOCK FLAG IS : UNLOCK, SKIP VERIFY!!!`

系统侧：

```bat
adb shell getprop ro.boot.flash.locked        :: 期望 0
adb shell getprop ro.boot.verifiedbootstate
adb shell getprop ro.boot.slot_suffix         :: 应为 _b
```

## 常见报错（来自你的指南，仍然适用）

| 报错 | 处理 |
|---|---|
| `find port failed` | 没进 BROM：换按键组合 / 重插线 / 重开 |
| `usb_send failed(0/1)` | 拔线重连，重新进 BROM |
| 提示按任意键但 COM 口还没出现 | 先等设备管理器出现 COM 口再按键 |

## 一个需要你先确认的问题

**你的设备现在能正常开机吗？解锁之后 U-Boot 本来就会跳过镜像校验**
（走 `Device Status is unlock, skip %s image verify!` 这条路径）。

所以：

- 如果你只是要 **root（SukiSU）** → **可能根本不需要改 uboot**，解锁后直接
  `fastboot flash init_boot_b <你的 SukiSU init_boot>` 就行。
- 如果你要的是 **去掉「已解锁」那几行提示 + 启动静默** → 才需要第 1/2 步。

**先告诉我设备当前的启动状态和 UART 输出**，我再确认要不要走第 2 步。

## 禁止事项

- ❌ 不要刷 `splloader`（fused 设备上 SPL 被 RSA 校验，改了必砖）
- ❌ 不要刷 `uboot_b_patched_skipverify.bin`（签名与 hash 已破）
- ❌ 不要用 `w uboot`（分区名有歧义，会命中 slot A）
- ❌ 不要动 `miscdata` / `misc`（解锁状态已经写好了）
