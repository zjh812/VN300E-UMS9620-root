# T9100 — 刷写范围与风险评估

## 一、刷完整镜像会写哪些分区？

**只写 `uboot_b` 一个分区，3MB（0x300000）。别的什么都不碰。**

命令：
```
spd_dump --wait 300 exec_addr 0x65012f48 fdl fdl1-dl.bin 0x65000800 ^
         fdl fdl2-dl.bin 0xb4fffe00 exec w uboot_b full.img reset
```
其中只有一条写命令 `w uboot_b full.img`。

**实证**：你上次刷探针时的 spd_dump 日志里，只有这一条写记录：
```
Device is using slot b
file size : 0x300000
Write Part Done: uboot_b, target: 0x300000, written: 0x300000
```

日志里还出现的 `pgpt.bin`、`partition_1790859644.xml` 是**写到你本地工具目录的文件**，
不是设备分区 —— 那是 spd_dump 读回分区表后在本地存的副本。

| 分区 | 是否被写 |
|---|---|
| `uboot_b` | ✅ **唯一被写** |
| `splloader` | ❌ |
| `sml_a/b`、`trustos_a/b`、`teecfg_a/b` | ❌ |
| `miscdata`、`misc` | ❌ |
| `vbmeta_a/b`、`vbmeta_system/vendor/product/odm` | ❌ |
| `boot_a/b`、`init_boot_a/b`、`vendor_boot_a/b` | ❌ |
| `super`、`userdata`、GPT 本身 | ❌ |

## 二、会黑砖吗？

**不会变硬砖。最坏情况是可恢复的软砖。**

### 为什么不可能硬砖

1. **BootROM 是掩膜 ROM**，物理上无法被刷写 —— BROM 下载模式永远可用，
   与 `uboot` 是否完好无关。
2. **`splloader` 没被动** —— 引导链的第一级完好，你仍然能进 FDL1/FDL2。
3. **恢复链路你已经实证跑通过**：备份、解锁、刷探针，走的都是
   `BROM → FDL1 → FDL2 → 写分区` 这条链。写回原厂 `uboot_b` 是同一套命令。
4. 你有**全分区备份**（含 `splloader.bin`、`uboot_a/b.bin`、`miscdata.bin` 等）。

### 三种可能结果

| 情形 | 现象 | 处理 |
|---|---|---|
| magic64 生效 | ✅ 正常启动，`flash.locked=0` | 完成 |
| magic64 没跑 | 启动行为与 stock **完全一致**（payload 逐字节未改） | 设备无损，停下分析 |
| 入口点假设不成立 | uboot 起不来 → 黑屏 / 卡住 | 进 BROM 写回原厂 `uboot_b`，几分钟恢复 |

### 唯一真正需要防的

**断电/断线发生在写入的那几秒内。** 这是任何刷机都有的通用风险。
→ 电量充足、用数据线（非充电线）、全程别碰线。

## 三、比"黑砖"更可能发生、也更该提前准备的两件事

### 1. `verifiedbootstate` 会从 green 变成 orange（必然）

patch ① 让 `[0x2CADA0] = 2`，而 verifiedbootstate 跳表（code `0xC7C90`）
state 2 → `androidboot.verifiedbootstate=orange`。

这是**解锁设备的正常表现**，但意味着部分银行 / DRM / 支付类 App 可能拒绝运行。

### 2. **可能要求清除 userdata**（这条最重要）

Android 检测到 verified boot 状态从 green 变 orange 时，**首次开机可能要求
恢复出厂 / 格式化 userdata**。你自己的《解锁与刷入指南》里也写了这条：
> "先备份平板里的个人数据：解锁后首次开机可能要求恢复出厂/格式化 userdata"

**→ 刷之前先把平板里的个人数据备份出来。**

## 四、想更稳的话：先用「零影响探针」

如果你希望**在承担上面两个风险之前**，先确认 magic64 机制在这台机器上到底跑不跑，
可以先用这个探针：

```
T9100_uboot_b_probe_lockmsg_magic64.img
sha256 = e629c2f7028acacfe2ff1a76607af65b3caa6f905f91dbfaa4a0990d1c723c4e
```

它**只做一件事**：把 code `0xB520`（LOCK 分支里 `INFO: LOCK FLAG IS : LOCK!!!` 的
UART 打印 `bl`）改成 `nop`。

| 对比项 | 完整镜像 | LOCK 消息探针 |
|---|---|---|
| 写入分区 | `uboot_b` | `uboot_b` |
| 改动的指令 | 4 处 | 1 处 |
| 跳过镜像校验 | 是（patch ①） | **否** |
| `verifiedbootstate` | green → orange | **不变** |
| 触发清 userdata | 可能 | **不会** |
| 可观测效果 | `flash.locked=0` | LOCK 那行日志消失 |

### 为什么它需要一个额外步骤

`uboot_log` 是 16MB **环形缓冲**，旧内容会残留。而"删掉一行日志"这种效果
没法用"某个字符串以前没出现过"来判定（那行以前出现过 67 次）。
所以要先把它擦干净：

```bat
:: 1) 擦掉日志分区（只是日志，安全）
spd_dump --wait 300 exec_addr 0x65012f48 fdl fdl1-dl.bin 0x65000800 fdl fdl2-dl.bin 0xb4fffe00 exec e uboot_log reset

:: 2) 刷探针
spd_dump --wait 300 exec_addr 0x65012f48 fdl fdl1-dl.bin 0x65000800 fdl fdl2-dl.bin 0xb4fffe00 exec w uboot_b probe_lock.img reset

:: 3) 拔线，正常启动一次（等 10 秒）

:: 4) 读回日志
spd_dump --wait 300 exec_addr 0x65012f48 fdl fdl1-dl.bin 0x65000800 fdl fdl2-dl.bin 0xb4fffe00 exec r uboot_log reset
```

然后数 `INFO: LOCK FLAG IS : LOCK!!!` 出现次数：
- **0 次** → ✅ magic64 生效，可以放心刷完整镜像
- **1 次** → ❌ magic64 没跑，设备无损，停下分析

---

## 五、两条路怎么选

| 你的偏好 | 建议 |
|---|---|
| 想最快出结果，且已备份数据 | 直接刷完整镜像，用 `flash.locked=0` 判读 |
| 想先零风险验证机制 | 先走第四节的 LOCK 消息探针 |
| 设备里有重要数据还没备份 | **先备份，再决定** |

无论哪条路，回滚命令都一样：
```bat
spd_dump --wait 300 exec_addr 0x65012f48 fdl fdl1-dl.bin 0x65000800 fdl fdl2-dl.bin 0xb4fffe00 exec w uboot_b "C:\Users\admin\Desktop\B\T9100\backup\T9100_back\uboot_b.bin" reset
```
